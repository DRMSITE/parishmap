# Deploying and upgrading

## The checks to run

A change that looks harmless can break sign-in or the rules, and nobody on a parish council wants to find that out from a councillor. Before you deploy a change, and before you share a new version, run these:

```bash
npm run typecheck && npm run lint && npm test      # always
npm run test:e2e                                    # anything visible (needs: npx playwright install chromium)
npm run test:rules                                  # anything touching firestore.rules or Firestore code
```

`test:rules` needs Java 21 or later and the Firebase CLI, and starts the Firestore emulator. On
Windows it can leave a `java` process holding port 8080, which makes the next run fail with "port
taken". Check that its command line mentions `cloud-firestore-emulator` before you stop it, so that you do not end some other Java program by mistake.

## Deploying

Putting a build live is a short sequence, but the order matters, and one shortcut in particular is dangerous.

```bash
npm run build           # writes firebase.json and the function settings, then builds
npm run check:dist      # nothing that should not be public
firebase deploy --only firestore:rules
firebase deploy --only functions,hosting
```

Deploy rules before the site that depends on them, so that the new site never meets old rules, and deploy `functions` whenever `functions/` or your
tile settings change (`functions/tiles.config.json` is regenerated by `npm run build`).

**Never deploy straight after `npm run test:e2e`.** The end-to-end tests build a copy that skips
sign-in into `dist/`, which is also what Hosting serves. Always run `npm run build` immediately
before a hosting deploy, and `npm run check:dist` to prove it. The scan fails if the example
local-data content is in the build.

Firebase says "Skipped (No changes detected)" for a function it already has. That is not an error.

### A first look without risk

Replacing the live site is not something to do on a hunch. A Hosting preview channel gives you a temporary address to check a build before it replaces the
live site:

```bash
firebase hosting:channel:deploy preview --expires 1d
```

Add that address to the browser API key's referrer list first, or the site will not load Firebase.

## Upgrading ParishMap

New releases arrive in the public repository, and your own settings must survive the move. The steps are short.

1. Read the [CHANGELOG](../CHANGELOG.md) for the versions between yours and the new one.
2. Fetch the new version into your fork (`git fetch upstream && git merge upstream/main`), keeping
   your `deployment/` folder and `.env` (they are not tracked by the public repository, so a merge
   leaves them alone).
3. `npm install`, then the checks above.
4. Deploy: rules first, then functions and hosting.

If a release changes `firestore.rules`, the changelog says so, and the rules should go out together with the site.

## Upgrading dependencies

A newer version is not a reason to upgrade, and I would leave a working dependency alone until there is one. When you do upgrade, two cases need particular care.

- **Web Awesome:** its `wa-page` injects one `<style>` whose hash is in the Content Security Policy
  in `firebase.template.json`. If an upgrade changes that style, the phone navigation breaks and
  the browser console reports the new hash to put in the template. `e2e/csp.spec.js` catches it, which is a good reason to run it.
- **Firebase and Leaflet:** run the full set of checks, including `test:rules`.

In automated builds, install with `npm ci` so that the lock file is honoured and the versions you tested are the versions you ship.

## Rolling back

A bad release is easier to undo than it feels, though only partly. Hosting keeps earlier releases (Firebase console, Hosting, Release history: Rollback). Rules and
functions are redeployed from an earlier commit. Data is not rolled back by any of this, so a release that damaged records needs the backups; see
[backups.md](backups.md).
