# AGENTS.md

Instructions for AI coding assistants working in this repository (Claude Code, Codex, Cursor, Copilot and others). `CLAUDE.md` imports this file, so there is one set of rules.

ParishMap (DRMSITE LTD, AGPL-3.0-or-later): a private, login-only map and project planner that a parish, town or community council deploys to its own Firebase project. Everything particular to one council lives in `deployment/` (git-ignored; `deployment.example/` stands in until it exists): `parish.config.js`, an optional `boundary.geojson`, and Firebase web settings in `.env` (`VITE_FIREBASE_*`, see `.env.example`). See `README.md` for what it is and `docs/` for set-up, configuration, tile providers, roles, security, data protection and architecture (`docs/architecture.md` is the long form of the map below). Keep the docs in step with the code when behaviour changes.

## Project map

```
src/main.js          picks the start-up: boot/secure.js (default) or boot/local.js (VITE_LOCAL_DATA=true builds only)
src/boot/            secure.js: sign-in gate, Firestore data, role guard, router start/stop; local.js: no sign-in (dev and e2e)
src/config.js        the council's settings (from virtual:parish-config, checked by checkParishConfig), tiles (virtual:parish-tiles), limits (title, notes, vertices), storage prefix
src/routes.js        route table; views are lazy-imported
src/types.js         JSDoc typedefs only: GeoRecord, DataSource (the back-end seam), Guard, AppContext, ParishConfig
src/router/          history-API router (start and stop)
src/views/           one file per page: render(container, ctx), may return a cleanup function
src/map/             Leaflet map, basemaps (built from the tile providers), proxied-layer (keyed tiles through our function), markers, shapes (lines and areas), draw (click-to-add-vertices), boundary and boundary-file (optional council outline), leaflet-assets
src/tiles/           providers.js (provider data and checks; never import it from browser code), attribution.js, wording.js (words for Help and About about the chosen map)
src/icons/           the Font Awesome Free SVGs the app uses, registered in src/web-awesome.js
deployment.example/  stands in for the git-ignored deployment/ (council settings and optional boundary.geojson)
scripts/             admin and build scripts: setup, configure-auth, generate-config, parish-plugin (Vite plugin), check-dist, set-role, export-people, project-id, deployment-dir
docs/                user and contributor documentation
firebase.template.json  source of the generated firebase.json (edit this, not firebase.json)
src/auth/            session.js (sign-in state machine), firebase-auth-api.js, guard.js (guards, ForbiddenError), project-guard.js (who may do what with projects), people.js (client for the `api` function)
src/firebase/        config.js (public web config), app.js (the one app, auth and db)
src/ui/              sign-in screens, add/edit point dialog, delete confirmation, project, action and note dialogs, feature-picker (choose linked map features)
src/data/            data sources: firestore-source.js (real), local-source.js (dev), query.js (shared filtering); firestore-projects.js (real) and local-projects.js (dev) for projects, actions and notes
src/projects/        the projects feature, shared by both data sources and the views: model.js (lanes, statuses, limits, checks, ordering), convert.js (stored data to records), board.js (the actions board), tree.js, places.js (linked map features), format.js, errors.js
src/state/flags.js   show/hide flags
src/util/            DOM and geometry helpers (geo.js also validates GeoJSON)
functions/          Cloud Functions (Admin SDK, never in the browser): index.js (`tiles` and `api`), tiles-handler.js (the tile proxy's decisions) and people-handler.js (who may invite, change or disable whom); both handlers are plain functions so they can be unit tested. tiles.config.json is generated
firestore.rules      THE security boundary: roles, MFA, field validation, ownership
test/                Vitest unit tests; test-rules/ runs against the Firestore emulator; e2e/ holds Playwright and axe tests
```

## Stack and conventions

- Vanilla JavaScript (ES modules) with JSDoc types, checked by `npm run typecheck`. No TypeScript files, no UI framework.
- Vite for dev and build; Leaflet 1.9 with OpenStreetMap; Web Awesome (free package, imported per component in `src/web-awesome.js`, not via the autoloader).
- Biome for lint and format (2 spaces, double quotes). Vitest for unit tests, Playwright and axe for e2e.
- UK English in comments, docs and UI text.
- Do not commit or push unless the maintainer asks.
- Prefer the smallest change that solves the problem, and reuse existing helpers (`actionButton`, `confirmDelete`, `createPointDialog`, `escapeHTML`, `parseLat`) before writing new ones.

## Rules worth remembering

- Stored data is reached only through `ctx.data` (the `DataSource` typedef in `src/types.js`). Do not read or write storage from views.
- Every create, read, update and delete goes through the guarded `ctx.data` (`guardDataSource` in `src/auth/guard.js`, wired in `boot/secure.js`); views ask `ctx.guard.can(action, record?)` before offering Add, Edit or Delete. The real guard is `createRoleGuard` (admin and clerk: everything; councillor: read, add, change own; member: read). Guards are a UI convenience, not security: `firestore.rules` makes the same decision on every request, and the two must be kept in step (roles in `session.js` `ROLES`, the guard, and the rules). Never call the unwrapped source from a view.
- Sign-in: everyone must verify their email, enrol an authenticator app (TOTP) and sign in with a code. Firebase has no "require MFA" switch, so `session.js` forces it and the rules refuse any token without `sign_in_second_factor`. The sign-in screen has a "Forgotten your password?" form (`session.sendPasswordReset`): Firebase emails the link, and the answer is the same whether or not the address has an account. Roles are custom claims set only by the Admin SDK; never write a role from client code. Firestore cannot store nested arrays, so geometry is stored as a JSON string and validated by `parseGeometry` on write and read.
- `VITE_LOCAL_DATA=true` builds skip sign-in and use localStorage. It exists for development and the Playwright map tests only; never set it for a deployment. A normal build must not contain `boot/local.js` or the local source (check `dist/` if in doubt). Beware: `npm run test:e2e` builds the local-data build into `dist/`, which is also what Hosting deploys. Always run `npm run build` immediately before a hosting deploy (`npm run build && firebase deploy --only hosting --project <your-project-id>`), and never deploy straight after an e2e run.
- Web Awesome's page styles override the `hidden` attribute on slotted elements; `[data-chrome][hidden]` in `app.css` restores it. Use `data-chrome` for anything that must stay hidden until sign-in.
- The add/edit dialog (`src/ui/point-dialog.js`) is shared by the map and the Points list; the delete confirmation is `src/ui/confirm.js` (a `wa-dialog`, not `window.confirm`). Look form fields up with `querySelector('[name=…]')`, not `form.elements`, so they resolve before Web Awesome has upgraded them.
- Anything that opens the location field must load `src/map/leaflet-assets.js` first (it sets the global `L`, loads Leaflet's CSS and fixes the default marker image paths). Otherwise a deep link to `/list` makes the component fetch Leaflet from unpkg, and the pin image resolves to `index.html` (a 200 with zero width).
- Lines and areas: drawn natively in `src/map/draw.js` (no drawing plugin; Leaflet-Geoman was rejected as about 4 MB with lodash and Turf for what is a click-to-add-vertices tool). A shape is edited as text, one `latitude, longitude` per line, in the shared dialog (also the keyboard route); an area with holes, or several areas, can only have its title and notes changed. Leaflet paths cannot take focus, so each shape also has a marker at its representative point. The parish boundary (`boundary.geojson`, lazy-loaded) is a fixed layer with its own flag, not a record.
- Map tiles: OpenStreetMap by default; a council may choose Ordnance Survey (`os`) or its own provider in `tiles` in `deployment/parish.config.js` (docs/tile-providers.md). Providers are plain data in `src/tiles/providers.js`: `direct` (the browser fetches them) or `proxied` (our `tiles` function adds a key held in Secret Manager). The settings are checked, and the server-only fields (upstream address, secret name) removed, at build time by `scripts/parish-plugin.mjs`, which serves `virtual:parish-config` and `virtual:parish-tiles` to the browser; never import `providers.js` or `parish.config.js` from browser code (`npm run check:dist` fails if a secret name or upstream host reaches the bundle). `src/map/basemaps.js` builds layers (attribution always shown, handing over to OpenStreetMap beyond a provider's last zoom or when the person's role is not allowed); `src/map/proxied-layer.js` sends the sign-in token in `X-Firebase-Token` and shows tiles from blob URLs. The function (`functions/tiles-handler.js`, settings from the generated `functions/tiles.config.json`) is an allow-listed proxy: sign-in with second factor, the provider's roles, known style, tile inside `bounds` and the zoom range, private cache no longer than the provider's limit; keep those guards when changing it. No pre-fetching, offline copies or service worker for third-party tiles. `ctx.tiles` exists only in the signed-in start-up. `firebase.json` and `functions/tiles.config.json` are generated by `npm run generate` (also run by `build`, `test:rules` and `test:e2e`) from `firebase.template.json`: edit the template, never `firebase.json`. The CSP in `firebase.json` is a hard allow-list: a Web Awesome upgrade that changes the `wa-page` style hash needs the hash in `firebase.template.json` updating. The Hosting emulator does not apply custom headers, so `e2e/csp.spec.js` applies the real policy from `firebase.json` to the page and fails on any `securitypolicyviolation` while the main screens and dialogs are used. Add to that test when you add a screen that loads something new (the Add point dialog's own map asks for tiles from `a.`, `b.` and `c.tile.openstreetmap.org`).
- Managing people: the People page (`src/views/people.view.js`, Clerk and admins only) calls the `api` function through `src/auth/people.js` (token in `X-Firebase-Token`, same-origin `/api/people`; Hosting rewrites `/api/**`, Vite proxies it in development). The function, not the browser, decides: an admin may do anything except to themselves; a clerk may only invite or change councillors, members and people with no role, and assign only councillor or member; nobody changes their own account. Inviting creates the account with a random password and the role, then the browser asks Firebase to email a set-password link (`sendPasswordResetEmail`). Disable, role change and authenticator reset all sign the person out everywhere. Every action is written to `auditLog` (admin-readable, never client-writable); administrators read it on the Activity page (`src/views/activity.view.js`, through `ctx.audit`, 50 entries at a time). `src/auth/people.js` mirrors the permission helpers only to hide buttons; keep it in step with `functions/people-handler.js`. Local mode uses an in-memory stand-in (`src/data/local-people.js`).
- The Help page (`src/views/help.view.js`) is the user guide: everyone sees the general part, and the Clerk's part (inviting, lost phone, disabling) only appears when `ctx.people.available()`. It describes the screens as they are, so update it when sign-in, the map buttons or the People page change. It has no in-page contents links because the router ignores links to the current page.
- The map covers the council's area only: `minZoom` and `bounds` in `deployment/parish.config.js` stop zooming out and panning beyond it, and the add/edit dialog refuses any position outside the bounds (it could never be panned to). Wording that names the council, its kind or the Clerk comes from `config.council` (`src/config.js`), never hard-coded; `checkParishConfig` reports a bad file with every problem at once. OS tiles are cached by the browser for 7 days (`TILE_CACHE_SECONDS` in `functions/tiles-handler.js`, `private` so the Hosting CDN never keeps them).
- Projects, actions and notes (Projects page `/projects`, one project at `/projects?p=<id>`): three Firestore collections (`projects`, `actions`, `notes`) reached only through `ctx.projects` (the `ProjectsStore` typedef in `src/types.js`), never from a view and never unwrapped: `boot/secure.js` wraps the store with `guardProjects` (`src/auth/project-guard.js`), which throws `ForbiddenError` before a write the rules would refuse. Rules, mirrored by the guard and to be kept in step (`firestore.rules`, `project-guard.js`, `test-rules/projects.test.js`): admin and clerk create top-level projects, name the responsible person and may do everything; the responsible councillor edits their project, adds sub-projects under it (becoming responsible for them) and moves actions; any councillor adds an action (only to the Ideas lane unless they manage the project) or a note, and edits or deletes their own; only the responsible councillor, clerk or admin may change an action's `lane` or `order`; members read only. Nobody but admin or clerk changes `responsibleUid`, and a project's `parentId` is fixed. Every document carries `createdBy`, `updatedBy`, their emails and times, all checked by the rules. Sub-project depth (`config.limits.projectDepth`) is enforced in the app only, because rules cannot count it. Firestore has no cascade delete, so `removeProject` deletes the sub-projects, actions and notes in batches, and only admin or clerk may; notes about a deleted action stay and are shown as such. Moving a card has two routes that must stay equivalent: the "Move to" list with Move up and Move down buttons (keyboard, touch, screen reader) and drag and drop (mouse); `src/projects/board.js` offers both only to people who `can.canMoveActions`. Positions are numbers placed between neighbours (`orderBetween`), so equal values from simultaneous moves are tolerated and sorted by `createdAt` then id. Names come from the `directory` action of the `api` function (id and email of enabled admins, clerks and councillors, open to those three roles and never to members), cached by `cacheDirectory`; records also keep the email beside each uid so a name can still be shown if the directory cannot be reached. Projects and actions link to existing map features by id (`featureIds`, at most `config.limits.featureLinks`); a link to a deleted feature is shown as removed, never an error, and links open the map at `/?place=<id>` (`map.view.js` frames the place and opens its popup). The reverse link is shown in both the map popup (`PopupActions.extra`) and the Points list, which must stay equivalent: `projectsForFeature` (`src/projects/links.js`) finds the projects that link to a place directly or through one of their actions, and `loadProjectsQuietly` means a view never fails because projects could not be read. Stored projects are untrusted: `src/projects/convert.js` drops anything malformed. Help and About describe all this and must be kept in step.
- Set-up tooling (docs/firebase-setup.md, docs/backups.md): `npm run setup` (`scripts/setup.mjs`, pure parts in `scripts/setup-lib.mjs`) writes `deployment/parish.config.js`, `.env` and `.firebaserc` and never overwrites without `--force`; `npm run configure-auth` (`scripts/configure-auth.mjs`) shows, and with `--yes` applies, the Identity Platform settings (email sign-in on, sign-up off, TOTP available) using Application Default Credentials and a `.firebaserc` or `FIREBASE_PROJECT` project. It has not been run against a new project yet. Admin scripts take the project from `scripts/project-id.mjs`, never a built-in id. A pasted answer must stay readable in `line()`: the set-up script reads every answer through one async line reader so piped answers are not lost.
- The maker's credit (`NOTICE`): `ParishMap, built by DRMSITE LTD` stays in the navigation footer (`index.html`, `.credit`) and in the About page's "About this software" section, both from the details in `src/branding.js`. It is not a council setting, so do not add a switch to hide it; the council's own name leads everywhere else. The one configurable thing is `sourceUrl` (where the AGPL source is offered from, for a council running a modified copy). Do not make the About page claim anything about where the data is stored: that depends on the council's Firestore location.
- Show/hide options are flags (`src/state/flags.js`); do not add bespoke toolbar toggles.
- Views return a cleanup function; the map view must destroy its map (`handle.destroy()`).
- Never put record content into `innerHTML`. Use DOM nodes or `escapeHTML`.
- Leaflet in containers that may be hidden: keep the `ResizeObserver` approach in `src/map/map.js`; never initialise a map at zero size.
- Web Awesome: value events are `change` (not `wa-change`); hints use the `hint` attribute; name icon-only buttons with `label` on the `wa-icon`; `aria-pressed` on a `wa-button` host is not forwarded. Use plain `<a>` for navigation (a link inside a shadow root is invisible to the router's click handler).
- Page shell is `<wa-page>` (3.14). Slot `header`, `navigation` (becomes a drawer below 768px) and a `<main id="main-content">`; do not add our own skip link, wa-page's is the only one (its target is `#main-content`). Its default hamburger has no accessible name, so `index.html` slots our own `navigation-toggle` button with a labelled icon. wa-page publishes `--header-height`; use it to size full-height content. Web Awesome's native styles pad `<main>`, which `app.css` resets. axe reports the built-in skip link under `region`; `e2e/axe.js` filters that single node and nothing else.
- The router does not move focus on the first render (so Tab reaches the skip link first); it does on later in-page navigations.
- Web Awesome is the free, MIT-licensed `@awesome.me/webawesome` package (including `wa-page`, free since 3.5): no token or `.npmrc`. Icons are not fetched from Font Awesome's CDN: `src/web-awesome.js` registers the SVGs in `src/icons` (Font Awesome Free, CC BY 4.0; keep each file's licence comment) as the default library, so a new icon means copying its SVG from `svgs/solid`. A `wa-icon` with an unknown name renders blank without an error, so check by eye or in the browser.
- `wc-location-field` (Add a point dialog): light DOM, IIFE build that finds Leaflet through the global `L` (set by our bundled Leaflet, so it never fetches unpkg). Import it lazily and create the element on the dialog's `wa-after-show` (never at zero size); remove it on `wa-after-hide`. `prefill({ lat, lng })` moves the pin without emitting or geocoding; `location-change` fires only for a map click, pin drag or chosen result. The lat/lng inputs stay the source of truth for saving. It calls Nominatim, which About discloses.
- Lat/lng inputs are `type="text"`, parsed with `parseLat` / `parseLng` in `src/util/geo.js`.
- Accessibility is a requirement (WCAG 2.2 AA): keyboard use, visible focus, labelled controls, no colour-only meaning, `prefers-reduced-motion` respected. The Points page is the text alternative to the map; keep it equivalent.
- Playwright's `fill()` obeys `maxlength` and truncates, so a save-time length check is only reachable by setting the element's `value` property.

## Checks

`npm run typecheck && npm run lint && npm test`, then `npm run test:e2e` for anything user-facing and `npm run test:rules` for anything touching `firestore.rules` or the Firestore source (needs Java; it starts the emulator, and on Windows may leave a `java.exe` holding port 8080, which makes the next run fail with "port taken"). Do not claim a check passed unless you ran it.
